# ADR-0009: Вынос адреса общежития в таблицу Buildings

- **Статус:** принято для релиза v1.9.0
- **Дата:** 2026-10-31
- **Задача:** CAMPUS-108

## Контекст

В исходной структуре адрес хранится в таблице `Dormitory`. По мере развития системы сведения о здании могут расширяться. Хранение адреса в таблице общежитий связывает данные о здании с конкретной записью общежития и затрудняет повторное использование информации.

## Решение

Создать таблицу `Buildings` с полями `Id`, `Address`, `CreatedAt`. В `Dormitory` добавить `BuildingId` как внешний ключ. На переходном этапе приложение записывает адрес в новую таблицу, а старое поле сохраняется до завершения миграции всех экземпляров.

Изменение выполняется в три фазы:
1. Expand — создать таблицу и nullable-ссылку.
2. Migrate — перенести исторические адреса и заполнить `BuildingId`.
3. Contract — после проверки сделать ссылку обязательной и удалить старое поле.

## Последствия

**Положительные:**
- структура данных становится понятнее;
- появляется отдельная сущность здания;
- миграцию можно выполнять постепенно;
- расширенная схема позволяет откатить приложение без немедленного возврата структуры БД.

**Отрицательные:**
- временно требуется поддерживать старую и новую структуру;
- запросы должны учитывать связь между таблицами;
- перед Contract необходимо проверить все экземпляры приложения и резервные копии.

## Рассмотренные альтернативы

1. Оставить адрес в `Dormitory` — проще, но задача разделения сущностей не решается.
2. Переименовать поле — не создаёт отдельную сущность и не даёт нужной структуры.
3. Сразу удалить старое поле — рискованно, потому что старая версия приложения может продолжать его использовать.

## Проверка решения

Решение считается успешно реализованным, если после миграции у каждой записи `Dormitory` заполнен `BuildingId`, адрес доступен через `Buildings`, а Sanity Test создания и удаления тестовой записи проходит успешно.
